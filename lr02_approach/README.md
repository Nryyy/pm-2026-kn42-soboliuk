# Вибір підходу для трьох проєктів

Студент: Соболюк Назарій, Nryyy. Тема проєкту: Платформа обліку практик і стажувань: студент, база практики, керівник, звіти.

## 1. Три кейси коротко

| Кейс | Обраний підхід | Критерій, який тягне проти | Ціна цього вибору |
| :-: | --- | --- | --- |
| C-1 | predictive | technology | ризиком технічної несумісності та переробками через нестабільне API |
| C-2 | adaptive | release_cost | додатковими витратами на жорсткий QA для розрахункових модулів |
| C-3 | hybrid | contract | швидкістю узгодження змін через бюрократію фіндиректора |

## 2. Кейс C-1

Конфлікт критеріїв: Контракт, вимоги, доступність замовника та ціна помилки суворо вимагають предиктивного підходу (fixed price, тендер, чіткий наказ, відсутність замовника на демо). Проте технологія (API реєстру) є нестабільною і тягне в адаптивний бік. Переміг предиктивний підхід, оскільки юридичні рамки та пеня не залишають простору для гнучкого планування бюджету та строків.

Що робимо з критерієм, який тягне проти: Запускаємо технічний Spike-етап на самому початку для дослідження API реєстру, створюємо заглушки (mock) і повністю ізолюємо шар інтеграції від основної системи, щоб мінімізувати вплив неоголошених змін методів.

Відкинутий підхід: Adaptive. Плюс: Змогли б миттєво і гнучко реагувати на часті зміни в API реєстру без зупинки процесу. Мінус: Неможливо застосувати через жорсткий тендерний договір, фіксовану дату подання та відсутність залученості замовника.

Перший тиждень: Зробити технічний спайк API реєстру, написати заглушки для тестового контуру та зафіксувати поточну поведінку методів.

## 3. Кейс C-2

Конфлікт критеріїв: Команда, вимоги, контракт та клієнт ідеально підходять для адаптивного підходу, оскільки продукт живе постійними гіпотезами та швидким зворотним зв'язком. Але ціна помилки для платіжної частини (release_cost) є високою (санкції банку, втрата грошей), що тягне до предиктивного підходу. Адаптивний переміг, бо стартапу життєво необхідно перевіряти продуктові гіпотези на ринку, інакше він помре швидше, ніж помилиться в розрахунках.

Що робимо з критерієм, який тягне проти: Відокремлюємо платіжний контур від загального продукту на рівні архітектури, запроваджуємо для нього жорсткий і розширений процес регресійного тестування перед кожним щотижневим релізом.

Відкинутий підхід: Predictive. Плюс: Надав би максимальну надійність та стабільність для розрахунку комісій та застав. Мінус: Стартап витратить гроші інвестора на розробку непотрібного ринку функціоналу без змоги швидко змінювати курс.

Перший тиждень: Відокремити платіжний контур від решти продукту, налаштувати для нього максимальне покриття автотестами та моніторинг.

## 4. Кейс C-3

Конфлікт критеріїв: Контракт (фіксований бюджет на рік, погодження фіндиректора) та критичність помилки в нарахуваннях диктують предиктивний підхід. Водночас мінливі вимоги (невідомі винятки договорів) та технологія (невідома якість старих даних) вимагають гнучкості. Гібрид переміг: фіксовані загальні рамки бюджету і дедлайну поєднуються з ітеративним виявленням вимог на демо з юристами.

Що робимо з критерієм, який тягне проти: Домовляємося про гнучкість у межах жорсткого fixed price через фіксований час та бюджет, але зі змінним обсягом (MoSCoW), щоб "обмінювати" новий функціонал на менш пріоритетний без збільшення кошторису.

Відкинутий підхід: Predictive. Плюс: Повністю задовольнив би фінансового директора завдяки чіткому та незмінному плану робіт. Мінус: Призвів би до розробки системи, якою ніхто не зможе користуватися, бо вона не враховує реальні винятки погоджень юрвідділу.

Перший тиждень: Зробити вивантаження та маппінг даних зі старої системи, провести настановну зустріч з юристами для збору перших винятків.

## 5. Стрес-тест контрактом

| Кейс | Рішення до конверта | Рішення після | Що змінилось у роботі PM |
| :-: | --- | --- | --- |
| C-1 | predictive (конфлікт: technology) | adaptive | Точка приймання зміщується на щотижневі демо, розробку можна планувати ітераціями паралельно зі стабілізацією API, ризик невідомих витрат переїхав на замовника. |

Окремо: що робить PM, коли контракт fixed price, а вимоги мінливі:
1. Запроваджує процедуру "Scope Swap" (обмін обсягом): дозволяє замовнику додавати нові вимоги лише за умови вилучення старих вимог аналогічної складності (ціна: витрати часу на переоцінку беклогу та складність підтримки архітектури).
2. Жорстко формалізує процес Change Request: будь-яка мінлива вимога має проходити оцінку впливу на гроші та час перед реалізацією (ціна: зниження швидкості розробки та потенційні конфлікти через бюрократію).

## 6. Власний проєкт

Тема: Платформа обліку практик і стажувань: студент, база практики, керівник, звіти.

Обраний підхід: adaptive (Scrum з фіксованим timebox на 16 тижнів).

Чому саме так: У моєму варіанті (V03) є крос-функціональна команда на 5,0 FTE (виділені Dev та QA на 100%), жорсткий дедлайн у 16 тижнів і бюджет 1,6 млн грн. Залученість замовника (керівник практики від факультету) на демо дозволить уточнювати реальні процеси кафедр. Адаптивний підхід безпосередньо ловить Ризик 1 з моєї ЛР1 (Big Bang реліз без пілоту): ітеративне постачання дозволить випустити робочий MVP для одного факультету, який стане повноцінним пілотом із чіткими критеріями успіху. Ми зберемо зворотний зв'язок від перших користувачів і лише на основі цих даних ухвалюватимемо рішення про масштабування платформи на всю академію. Від C-1 моя ситуація відрізняється тим, що тут немає тендерного fixed price із погодженням кожної зміни, а замовник (керівник практики від факультету) приходить на демо раз на два тижні, а не відповідає за 3-5 днів; команда виділена під проєкт, а не розкидана по містах. Від C-2 та C-3 вона відрізняється виділеним на 100% QA-фахівцем, що дозволяє делегувати контроль якості без відволікання розробників чи аналітиків; від C-3 ще й тим, що дату тут фіксує графік практики, а не річний бюджет, тож при нестачі часу ріжемо обсяг, а не переносимо реліз.

## 7. Робочий журнал

Під час читання кейсу C-2 спершу здавалося, що висока ціна помилки у фінансовому модулі має скасувати адаптивний підхід. Але згодом стало зрозуміло, що відмова від перевірки гіпотез у стартапі коштує ще дорожче — компанія просто збанкрутує, зробивши нікому не потрібний продукт. Тому залишив адаптивний підхід, а ризик фінансів перекрив локальним інженерним рішенням (відділення платіжного модуля). Для власного проєкту (V03) одразу обрав Scrum, оскільки наявність повноцінної команди з окремим QA ідеально лягає на 2-тижневі спринти.
